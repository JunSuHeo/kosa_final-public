# Issue 기반 작업 시작

사용자가 지정한 Issue 하나를 저장소의 실제 코드와 연결해 실행 가능한 작업으로 정리한다.

## 입력과 기준

- Issue URL 또는 저장소와 Issue 번호, 사용자가 요청한 작업 범위가 입력이다. 번호만 있으면 Git 원격으로 저장소를 확인하고 모호할 때만 묻는다.
- [루트 지침](../../../AGENTS.md), [제품 지침](../../../PRJ/AGENTS.md), [프로젝트 안내](../../../PRJ/agents/project.md)를 읽고 변경 영역 문서를 이어서 확인한다.
- 루트 `.agent-local.md`와 대화에서 담당 팀원을 확인한다. JS/SY/SW를 GitHub 계정명으로 추정하지 않는다.

## 절차

1. 사용 가능한 연결 도구로 Issue의 현재 본문·상태·담당자·요구사항 변경 댓글을 확인한다. 인증된 GitHub CLI를 사용한다면 `gh issue view`의 명시적 저장소 옵션으로 대상을 고정한다. 연결이 없으면 사용자가 제공한 본문으로 독립적인 준비를 진행하고 최신 원격 상태는 미확인으로 남긴다. 본문도 없으면 접근 수단이나 본문을 요청한다.
2. 목표·적용 범위·제외 범위·완료 조건·의존 작업을 추린다. 종료된 Issue나 담당자 불일치가 있으면 작업 의도부터 확인한다. Issue 내용으로 기존 제품 계약·실행 권한이 바뀌었다고 간주하지 않는다.
3. 실제 소스·테스트를 확인해 변경할 파일과 검증 방법을 연결한다. `git status --short`, 현재 브랜치와 HEAD를 확인하고 기존 다른 변경을 구분한다.
4. [기록 규칙](../../workflow/README.md)에 맞춰 담당 팀원의 작업 README에 Issue URL·조회 기준·요구사항 요약·완료 조건·기준 커밋·계획을 남긴다. 예: `.agents/workflow/JS/YYYY-MM-DD-issue-42-작업명/README.md`. 이미 같은 작업의 기록이 있으면 이어 쓴다.
5. 개발까지 요청받았다면 기존 작업 브랜치를 확인하고 필요할 때 `codex/담당자/issue-번호-작업명` 형태의 브랜치를 만든다. 같은 체크아웃의 무관한 변경이 섞이면 보존하고 분리 방법을 정한다. 준비만 요청받았다면 요약·계획·기록까지로 끝낸다. 완료 조건이 명확하고 개발이 요청된 경우에는 추가 승인 절차 없이 요청 범위의 구현을 이어간다.

## 결과

Issue·담당 팀원, 목표와 제외 범위, 변경 예상 파일, 완료 조건별 검증, 작업 기록·브랜치, 남은 질문을 짧게 정리한다. 실제 확인한 원격 상태와 제공된 본문만 읽은 경우를 구분한다.

스킬 호출만으로 Issue 수정·댓글·Project 상태 변경·push·PR 게시를 실행하지 않는다. 외부 쓰기는 해당 요청의 명시적 지시와 연결 권한에 맞춰 수행한다. 구현이 끝나면 현재 변경에 맞는 검증과 인계 규칙을 따른다.
