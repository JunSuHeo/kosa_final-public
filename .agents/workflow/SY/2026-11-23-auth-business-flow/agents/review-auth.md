# 인증·감사 이력 독립 리뷰

- 범위: `d3ca1a7` 대비 Task 1·2 인증 경계와 계정 관리 변경의 정적 리뷰. 제품 코드 수정 없음.
- 검증: 구현과 관련 테스트·제품 계약을 확인했다. 아래 시나리오는 코드 경로 분석이며 별도 실행하지 않았다. 실제 Supabase와 서비스 DB는 사용하지 않았다.

## 필수 수정

1. **감사 이력 새로고침 시 중간 페이지 누락** — `PRJ/frontend/src/UserManagement.tsx:81-86`. 기존 페이지를 읽은 뒤 새 감사 기록이 200건 넘게 추가되면, 자동 새로고침은 최신 200건만 앞에 붙이고 과거 `auditNext`를 그대로 둔다. 두 구간 사이 기록은 이후 오래된 기록 로드에서도 건너뛴다. 이미 불러온 경계까지 새 페이지를 이어 읽거나 빈틈을 복구할 수 있는 커서 관리가 필요하다. 초기 로드 후 201건 이상 추가한 시나리오로 확인한다.

2. **다른 재설정 작업에 밀린 작업 ID가 브라우저에 고착** — `PRJ/frontend/src/accounts/server.ts:51-60,103-105`, `PRJ/backend/app/accounts.py:331-335`. 탭 A의 재설정이 미완료된 후 탭 B 또는 다른 관리자가 같은 계정을 재설정하면 A의 재시도는 superseded 409다. A는 실패한 작업 ID를 계속 보존하여 다음 제출도 같은 409가 되므로 해당 계정을 다시 재설정할 수 없다. 이 충돌을 식별하여 사용자가 새 작업으로 진행할 수 있어야 한다. 일시 실패·재인증에 필요한 기존 ID 보존은 유지한다.

3. **응답 유실 후 다른 비밀번호 입력을 성공으로 오인** — `PRJ/frontend/src/accounts/server.ts:51-56,103-104`, `PRJ/frontend/src/UserManagement.tsx:411-421`, `PRJ/backend/app/accounts.py:312,324-330`. 첫 재설정이 완료됐지만 응답이 유실된 뒤 사용자가 다른 비밀번호를 입력하면 브라우저가 기존 operation ID로 보낸다. 완료된 서버 작업은 비밀번호를 비교하지 않고 성공을 반환하므로 UI는 새 입력의 변경 성공을 알리지만 실제 비밀번호는 첫 입력이다. 같은 문제는 계정 생성에도 적용된다. 비밀번호 및 검증값을 저장하지 않는 계약을 유지하면서 동일 입력 재시도와 명시적인 새 작업을 구분해야 한다.

## 인계

- 정적 확인만 수행했다. 수정 및 회귀 검증은 주 담당자가 수행한다.
- API 소유권·불변 revision 계약과 실서비스 데이터는 변경하지 않았다.

## 수정 1차 재검토

- **1번: ADDRESSED.** 최신 페이지와 기존 이력이 겹치지 않으면 목록과 커서를 같은 새 경계로 교체한다. 공통 항목이 있으면 기존 과거 커서를 보존한다. 교체 시 안내를 표시한다. `agents/sessions.md`에 기록된 route fixture 테스트가 201건 증가 및 402건 전체 조회를 검증한다.
- **2번: ADDRESSED.** 서버의 구조화된 `account_operation_superseded` 코드를 프런트가 식별해 해당 ID만 제거한다. 자동 재전송 없이 다음 명시적 제출에 새 ID를 발급한다. 동일 입력의 일시 실패·SPA 재인증은 기존 ID를 유지한다.
- **3번: NOT ADDRESSED.** 거짓 성공 경로는 차단했으나 새 수정으로 미완료 계정 생성의 복구가 막힌다. 생성 요청이 DB에 pending 계정과 operation을 기록한 뒤 Auth 503이 발생하고 페이지가 새로고침되면 `PRJ/frontend/src/accounts/server.ts:54-60`은 메모리 입력을 확인할 수 없다는 이유로 기존 ID를 새 UUID로 덮어쓴다. 새 ID를 받은 `PRJ/backend/app/accounts.py:340-344`는 이미 존재하는 login ID에 409를 반환하므로 기존 pending operation을 다시 실행할 수 없다. 기존 작업 ID는 브라우저에서도 잃는다. 비밀번호를 변경해 제출할 때도 같다. 기존 테스트는 완료된 create 후 새 ID의 409만 확인하며 pending create의 복구를 검증하지 않는다. 비밀번호나 검증값을 저장하지 않으면서 사용자가 기존 작업을 명시적으로 재개할 수 있는 경로가 필요하다.

재검토는 코드와 위임 담당자의 실행 기록을 확인한 정적 검토다. 브라우저·DB 테스트는 별도 재실행하지 않았다.

## 수정 2차 재검토

- **3번: ADDRESSED.** 기존 pending 생성은 동일 login ID·정규화된 이름·역할의 새 작업에서 같은 계정과 Auth UID를 사용해 현재 입력 비밀번호를 적용하고 완료한다. ready 중복과 메타데이터 불일치는 409다. 새 create 작업 이후 이전 미완료 작업은 superseded 409로 차단되어 최신 비밀번호를 덮지 않는다. 기존 완료 작업의 멱등 응답도 유지한다.
- 변경 범위에서 추가 필수 결함은 발견하지 못했다. 앞선 1·2번 수정은 이번 재검토 범위에서 변경되지 않았다.
- 코드와 `agents/sessions.md`의 격리 PostgreSQL 27개 및 production dist 브라우저 경계 15개 통과 기록을 확인했다. 독립 재실행과 실제 Supabase 검증은 하지 않았다.
