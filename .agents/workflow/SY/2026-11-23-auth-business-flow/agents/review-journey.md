# Task 3·4 독립 검토

- 범위: d3ca1a7 대비 현업 화면, App 통합과 탭 임시 저장. 인증 구현과 IT 관리 UI는 범위 밖.
- 방법: 승인된 plan.md, 관련 프런트엔드·백엔드 소스와 신규 테스트 정적 검토. 테스트 별도 실행 없음. 다른 에이전트의 실행 결과를 이 기록에 통과로 기재하지 않음.

## 중요 발견

1. **확인본 직접 편집이 기존 초안을 대체한다.** `PRJ/frontend/src/App.tsx:383-388,565-569`, `PRJ/backend/app/main.py:585-588`. 기존 pending 초안이 있을 때 사용자가 확인본을 선택하고 직접 편집하면, 화면은 확인본의 snapshot을 복제하지만 저장 요청에 pending proposal ID를 넣는다. 서버는 해당 초안을 superseded로 전환하고 확인본에서 편집한 snapshot으로 새 초안을 만든다. 기존 초안의 변경 사항이 빠질 수 있다. 확인본을 편집할 때 pending 초안이 존재하는 경로를 막고 초안으로 이동하게 하거나, 기존 초안을 보존할 명시적 설계가 필요하다. 신규 테스트는 proposal 없는 확인본만 다룬다.

2. **이전 프로젝트의 저장 응답이 현재 프로젝트의 편집을 닫는다.** `PRJ/frontend/src/App.tsx:556-575`. A에서 직접 편집 저장을 요청한 뒤 응답 전에 홈을 통해 B로 이동할 수 있다. B에 탭 임시 편집이 있으면 재진입 시 복원된다. 이후 A의 요청이 성공하면 A의 `discardEdit()`가 전역 `edit`를 null로 만들고 `showReviewGuide()`가 B 화면을 전환한다. B 임시 내용은 저장소에 남더라도 화면에서 사라지고 재진입이 필요하다. 요청 시작 시 프로젝트·계정과 후처리 시 현재 컨텍스트를 비교해야 한다.

3. **재진입한 검토 화면에서 저장된 질문 답변이 생성 차단을 우회한다.** `PRJ/frontend/src/App.tsx:240-249,508-512`, `PRJ/frontend/src/Chat.tsx:302-321`. pending proposal과 완료된 discuss 질문이 있는 프로젝트에서 질문 선택/직접 입력을 보관하고 새로고침하면 초기 진입이 review를 연다. Chat이 마운트되지 않아 `hasUnsent`는 false이고 생성 가드는 chat 입력 키만 읽는다. 예를 들어 blocking 초안의 ‘AI로 정리하기’가 보관 중인 질문 답변을 무시하고 실행된다. 현재 job의 질문 임시 저장도 Chat 마운트 여부와 관계없이 생성 전 검사해야 한다.

4. **생성 성공 뒤 목록 조회 실패가 재제출 시 중복 프로젝트를 만든다.** `PRJ/frontend/src/App.tsx:338-350`, `PRJ/frontend/src/BusinessHome.tsx:368-372`. POST가 프로젝트를 만든 후 `refreshProjects()`가 실패하면 `onCreate`는 실패로 반환하므로 입력이 남고 사용자는 재시도한다. 각 시도에서 새 UUID를 생성하므로 두 번째 프로젝트가 생긴다. 생성 POST 응답이 네트워크에서 유실된 경우도 동일하다. 같은 생성 시도의 ID를 재시도 동안 유지하고 부가 목록 조회 실패를 생성 실패로 취급하지 않아야 한다. 유사하게 `send`와 `submitAnswers`도 후속 refresh 실패를 전송 실패로 표시하므로 서버 성공과 UI 입력 정리를 분리할 필요가 있다.

5. **브라우저 이력 이동 시 질문·실패 재개 화면이 가려질 수 있다.** `PRJ/frontend/src/App.tsx:266-274,275-295`. 일반 `navigate()`와 달리 popstate는 `panel`, `sideOpen`, `mobileView`를 초기화하지 않는다. 다른 프로젝트에서 review를 연 상태로 브라우저 이력 이동으로 질문 대기 또는 실패 프로젝트에 들어가면 review가 유지되고 질문·재시도가 바로 표시되지 않는다. 산출물 이전 단계에서는 도구 목록이 chat만 남아 review가 선택된 상태와도 어긋난다. 초기 진입 시 상태에 맞는 패널과 모바일 뷰로 이동해야 한다.

## 인계

위 내용은 코드 경로의 정적 분석이며 별도 재현 테스트를 수행하지 않았다. 기존 E2E 실행 및 수정은 통합 담당자가 수행한다.

## 수정 후 재검토

- 범위: 최초 다섯 발견과 수정 diff, `journey.md` 추가 검증 기록 및 `app-journey-regressions.spec.ts`를 정적으로 다시 확인했다. 별도 테스트 실행은 하지 않았다.
- 1 확인본 편집: **해결**. pending이 있는 확인본의 편집 버튼과 `startEditing`을 함께 차단한다. 빈 revision 0에서도 저장된 초안의 검토 도구를 유지한다.
- 2 이전 프로젝트 저장 응답: **해결**. 요청 당시 계정·프로젝트와 편집 키를 캡처하고 성공 후 현재 컨텍스트가 다르면 화면 상태를 변경하지 않는다.
- 3 검토 화면 질문 초안: **해결**. 생성 시 현재 job의 질문 임시 저장을 직접 읽어 Chat 마운트와 관계없이 차단한다.
- 4 생성 재시도: **해결**. 같은 payload의 프로젝트·대화·생성 작업 ID를 보관하고 POST 성공을 후속 GET 성공과 분리한다. 백엔드의 동일 ID·동일 payload 반환도 확인했다.
- 5 브라우저 이력: **해결**. popstate가 대화 패널·모바일 뷰·열림 상태를 초기화하고 초기 진입 effect가 필요한 검토를 연다.

### 남은 발견

- **대화 전송 중 다른 화면으로 이동하면 성공한 입력이 남는다.** `PRJ/frontend/src/Chat.tsx:329-333`, `PRJ/frontend/src/drafts.ts:29-35`. 사용자가 A의 입력을 전송한 후 POST 응답 전에 다른 프로젝트나 홈으로 이동하면 A의 Chat은 언마운트된다. 성공 후 이전 Chat의 `setText`는 React의 언마운트된 state update가 되며, sessionStorage 쓰기는 그 updater 내부에만 있으므로 저장된 A 입력은 비워지지 않는다. A로 돌아가면 이미 서버에 전송한 내용이 미전송 입력으로 나타나 재전송할 수 있다. 성공 응답에서 요청 시 캡처한 키의 저장 내용을 현재 텍스트와 비교해 직접 지우는 처리가 필요하다. 정적 확인이며 별도 브라우저 재현은 하지 않았다.

`journey.md`에 기재된 focused 12개 통과와 격리 replay의 테스트 17개 통과/명령 exit 127은 구현 담당자의 보고다. 전체 격리 E2E는 통합 담당자가 별도 실행 중이다.
