## 1. GPT-6 Luna 실행 적용 및 실제 호출 확인

현재 `.env`의 `LLM_MODEL`과 `OPENROUTER_MODEL`은 `openai/gpt-6-luna`, `OPENAI_MODEL`은 `gpt-6-luna`다. API·worker 양쪽 설정 로드와 실제 호출을 확인했다. 앞선 localhost 연결 실패는 샌드박스 접근 제한이었으며 서비스 중지의 증거가 아니었다.

- [x] API·worker 실행 상태를 확인하고 두 서비스에 동일한 환경변수를 적용한다. 실행 명령은 [README](../README.md)를 따른다.
- [x] API 상태와 worker 설정이 모두 `live / openrouter / openai/gpt-6-luna`인지 확인한다.
- [x] 새 검증용 프로젝트에서 생성 → 질문 응답 → proposal 검토 → 승인 흐름을 확인한다.
- [x] AI 수정이 새 proposal을 만들고, 승인 전 확정 revision과 current_version을 변경하지 않는지 확인한다.
- [x] 다섯 역할 검토의 완료·근거 검증·실패 역할만 재시도를 확인한다.
- [x] 실제 호출의 모델·소요 시간·usage·비용·실패 내용을 기록한다. 근거 검증 실패 호출의 usage는 서버에 남지 않아 비용 미확인으로 구분한다.

증거: 생성(`luna-live-smoke.json`), 수정(`luna-live-revision-smoke.json`), 역할 최초 실패(`luna-live-review-smoke.json`), 실패 역할만 재시도(`luna-live-review-retry.json`).

완료 기준: Luna의 실제 생성·수정·역할 검토 결과와 서버 검증 결과를 증거로 남긴다. 기존 job은 생성 당시 공급자·모델에 고정되므로 새 모델 검증에는 새 job을 사용한다. 기존 Sol 검증 자료는 보존한다.

## 2. Supabase 실계정 로그인 검증

격리 자체 호스팅 Supabase Auth에서 실제 이메일/비밀번호 계정 두 개를 만들고 검증했다. 관리형 Supabase 프로젝트는 [준비 절차](supabase-verification.md)를 따른다.

- [x] 실제 Supabase 계정으로 로그인하고 인증된 API 요청을 확인한다.
- [x] 토큰 만료·잘못된 토큰의 401 처리와 UI 동작을 확인한다.
- [x] 서로 다른 계정으로 프로젝트·revision·proposal·job·역할 검토 접근 시 동일한 404로 차단되는지 확인한다.

완료 기준: 실계정 통합 검증 결과를 기록한다. 기존 JWT 단위 테스트 결과와 구분하고 토큰·키는 기록하지 않는다.

## 3. 다양한 도메인의 AI 품질·비용 반복 평가

- [x] 평가 도메인·입력·반복 횟수·품질 기준·비용 한도를 먼저 정한다.
- [x] 같은 조건으로 생성·수정·역할 검토를 반복 실행한다.
- [ ] 요청 반영, 산출물 간 일관성, 실제 사용 가능성, 검토 지적의 타당성을 사람이 평가한다.
- [x] 서버 검증 통과율과 의미적 품질을 구분하고 실패율·시간·토큰·비용을 집계한다.

결과: [6회 집계](luna-evaluation-report.md), 원시 수치(`luna-evaluation-summary.json`), 사람 평가표(`luna-human-review.md`). 최초 실행 기준 구조 통과 2/6, 요청 외 필드 변경 1/6, 역할 근거 검증 실패 8/30이다. 실패한 4개 사례를 성공 사례로 교체하지 않았다. 저장된 usage 보고 비용은 하한 US$0.10834927이며 실패 역할 8회의 비용은 미확인이다. 사용자 총평(`luna-user-feedback.json`)은 3/5점이며 실행별 네 항목의 의미 품질은 미평가다.

완료 기준: 평가 조건, 개별 실행 근거, 실패 사례, 집계 결과를 남긴다. 단일 사례의 성공을 일반적인 품질로 판단하지 않는다.
