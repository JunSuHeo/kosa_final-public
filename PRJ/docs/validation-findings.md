# 2026-11-10 검증에서 발견한 문제

## 수정 완료: API 교체 후 웹 502

- 우선순위: 높음. 모델 환경변수 적용처럼 API 컨테이너가 바뀌는 일상 작업에서도 화면이 연결되지 않았다.
- 재현: 기존 웹을 유지하고 API를 재생성한다. 기존 nginx가 이전 API IP를 참조하면 웹 `/health`가 502를 반환한다.
- 수정: Docker DNS로 API 주소를 재조회하는 nginx upstream 적용.
- 검증: 격리 환경에서 기존 IP를 다른 컨테이너가 점유하도록 하고 새 API를 실행했다. IP가 달라져도 웹 재시작 없이 약 10초 뒤 health·인증 API가 복구됐다. 증거(`proxy-recovery-verification.json`).

## 관찰: 좁은 수정 요청의 범위 초과

- 우선순위: 높음. 사용자가 요청하지 않은 문구가 바뀌어 수동 diff 검토가 필요하다.
- 재현 입력: `reading-2`의 첫 버튼 label 끝에 ` · 확인`만 추가하고 다른 필드·연결·순서를 유지하도록 요청했다.
- 관찰: 버튼 label 외에 `requirements[2].description`의 `날짜별 목록으로`가 `날짜별로`로 바뀌었다. 6회 중 1회다.
- 영향: 서버의 구조 검증은 통과했지만 정확한 변경 범위 검사는 실패했다. 확정본은 그대로였고 변경은 미승인 proposal에만 남았다.
- 후속: 사람 품질 평가에서 영향 판단. 좁은 수정의 적용 방식이나 프롬프트를 바꿀 경우 같은 고정 평가로 개선을 검증해야 한다. 이번 평가 결과를 좋게 보이게 하려고 실패 사례를 교체하지 않았다.
- 원시 근거(`luna-evaluation/reading-2.json`).

## 관찰: 역할 검토의 원문 인용 불일치

- 우선순위: 중간. 검토 완료율과 재시도 비용에 영향을 준다.
- 재현: 고정된 3개 도메인×2회에서 생성된 수정안을 다섯 역할로 검토했다.
- 관찰: 최초 30개 역할 중 8개가 서버의 ID/원문 일치 검사에서 차단됐다. 이를 검토 내용의 의미적 타당성 점수와 혼동하지 않는다.
- 보호 동작: 기획 데이터 불변, 잘못된 근거의 결과 미공개. 별도 smoke에서는 실패한 UI/UX만 재시도해 성공했고 완료된 네 역할은 동일하게 유지됐다.
- 후속: 역할별 프롬프트 개선이나 근거 선택 방식 변경은 별도 비교 평가가 필요하다. 서버의 인용 검증을 완화해서 통과시키지 않는다.
- 평가 집계(`luna-evaluation-summary.json`), 실패 역할 재시도(`luna-live-review-retry.json`).

## 관찰: 근거 검증 실패 호출의 usage 미보존

- 우선순위: 중간. 실제 비용을 완전하게 집계할 수 없다.
- 실패 지점: `role_reviews.py`의 `process_role`에서 모델 결과와 usage를 받은 뒤 `validate_evidence`가 예외를 발생시키면 실패 상태와 오류만 저장한다. 그 호출의 usage/response_id는 보존되지 않는다.
- 관찰: 반복 평가 8회와 별도 smoke 1회의 실패 호출 비용을 확인할 수 없다. 보고 비용은 하한으로 표시했다.
- 후속: 모든 시도의 usage 보존과 재시도 전후 이력을 설계하고, 거짓 근거 실패·재시도 성공에서도 두 호출 비용이 모두 남는 회귀 검증이 필요하다. 기존 실패 호출의 미저장 데이터를 추정값으로 복원하지 않는다.
- 이번 범위: 문제와 비용 누락을 기록했다. 제품의 비용 기록 구조 변경은 아직 구현하지 않았다.

## 환경 관찰: npm 취약점 보고

`npm ci`가 moderate 취약점 1개를 보고했다. 의존성 변경 없이 검증을 진행했으며 자동 `npm audit fix`는 실행하지 않았다. 취약 패키지·사용 경로·수정 버전의 별도 확인이 필요하다.
