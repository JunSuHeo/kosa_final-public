# AI 개발 자동화 시스템 요구사항

## 1. 문서 목적과 표현

이 문서는 여러 소프트웨어 프로젝트에서 재사용할 AI 개발 자동화 시스템의 제품 및 운영 요구사항을 정의한다. 자동화 시스템은 GitHub Issue를 작업의 출발점으로 삼아, Codex 에이전트가 승인된 범위 안에서 변경을 준비하고 테스트 근거와 함께 Pull Request(PR)를 사람에게 제출할 수 있도록 해야 한다.

이 문서는 요구사항만 정의하며 구현 방식, 구성 파일 형식, 서비스 및 기술 스택을 결정하지 않는다. 아래에서 **필수**는 시스템이 반드시 만족해야 하는 조건이고, **권고**는 프로젝트별 사유가 있을 때 예외를 기록하고 조정할 수 있는 조건이다. 구체적인 동작이 정해지지 않은 부분은 마지막의 [미결정 항목](#11-미결정-항목)에 모은다.

## 2. 목적과 범위

### 2.1 목적

- Issue에 기록된 문제와 완료 조건을 작업 가능한 변경으로 연결한다.
- 변경, 관련 설계 문서, 테스트 결과를 한 PR에서 검토할 수 있게 한다.
- 프로젝트별 규칙과 권한 경계를 지키면서 반복 가능한 작업 흐름을 제공한다.
- 자동화가 판단하지 못하거나 권한이 부족한 경우 그 이유와 필요한 사람의 조치를 명확히 남긴다.

### 2.2 포함 범위

- 설정된 GitHub 저장소에서의 Issue 작업 접수와 적격성 확인
- Issue 분석, 작업 계획, 관련 설계 문서 확인 및 필요한 문서 변경
- 승인된 범위의 코드·테스트·문서 변경
- 프로젝트 정책에 따른 Unit Test 및 E2E 테스트 실행과 결과 기록
- 변경을 별도 작업 브랜치에 제출하고 PR을 생성하거나, 차단 사유를 보고하는 과정
- 사람의 검토·승인·병합을 위한 정보 제공과 검토 의견에 따른 후속 수정

### 2.3 범위 밖

- 사람의 검토를 대신하는 자동 승인 또는 기본 자동 병합
- Issue에 근거하지 않은 기능 확장이나 별도 제품 작업
- 배포, 릴리스, 운영 환경 변경 및 저장소 설정·권한 변경
- 특정 모델, 에이전트 런타임, CI 제공자, 언어, 프레임워크, 패키지 관리자 또는 테스트 도구의 선택

## 3. GitHub Issue부터 PR까지의 흐름

시스템은 아래 흐름을 추적할 수 있어야 한다. 프로젝트 설정으로 달라지는 단계는 작업을 시작하기 전에 해당 설정을 확인해야 하며, 필수 설정이나 권한이 없으면 임의의 기본값을 만들어 진행하지 말고 차단 사유를 남겨야 한다.

1. **작업 접수 및 적격성 확인**
   - 설정된 저장소의 Issue 중 프로젝트 정책에 따라 자동화 대상으로 표시된 작업만 접수한다.
   - 저장소, Issue 상태, 자동화 대상 표시, 권한 및 필수 설정을 확인한다.
   - Issue가 닫혔거나 이미 처리 중이거나 대상 여부가 불분명하면 중복 작업을 시작하지 않고 상태를 기록한다.
2. **요구사항 분석**
   - 문제, 완료 조건, 제약, 재현 방법을 읽고 필요한 저장소 지침과 현재 설계 문서를 확인한다.
   - 작업 범위와 검증 방법을 정리한다. 완료 조건이 모호하거나 상충하면 추측으로 요구사항을 늘리지 말고 사람의 설명을 요청한다.
   - 유사하거나 중복된 Issue가 확인되면 관련 정보를 기록하고 프로젝트 정책에 따라 진행 여부를 결정한다.
3. **작업 공간과 변경 계획**
   - 기본 브랜치 및 브랜치 보호 규칙을 존중하는 격리된 변경 환경에서 작업한다.
   - 변경 대상, 영향 범위, 문서 변경 필요성, 실행할 테스트를 계획한다.
   - Issue와 무관한 기존 변경을 포함하거나 덮어쓰지 않는다.
4. **문서 및 제품 변경**
   - 본 요구사항의 설계문서 관리 규칙에 따라 필요한 설계 문서를 갱신한다.
   - Issue의 완료 조건에 필요한 최소 범위의 코드·테스트·문서 변경을 수행한다.
5. **검증**
   - 프로젝트에 설정된 필수 검사와 관련 Unit Test 및 E2E 테스트를 실행한다.
   - 결과를 성공, 실패, 실행 불가 또는 해당 없음으로 구분하고 근거를 기록한다. 실행하지 않은 검사를 통과한 것처럼 표시하지 않는다.
6. **PR 사전 확인 및 제출**
   - 변경 diff가 Issue 범위 안에 있는지, 문서와 구현이 일치하는지, 비밀정보가 포함되지 않았는지 확인한다.
   - 필수 검사가 통과하면 검토 가능한 PR을 생성하고 Issue를 연결한다.
   - 필수 검사가 실패하거나 실행 불가한 경우에는 정상 검토용 PR로 표시하지 않는다. 프로젝트가 허용하고 사람의 도움이 유용한 경우에만 실패 상태와 사유를 명시한 Draft PR을 생성할 수 있다.
7. **사람 검토 및 후속 처리**
   - PR에는 작업 요약, Issue 링크, 설계 문서 변경 여부, 테스트 명령과 결과, 남은 위험·제약을 제공한다.
   - 검토 의견에 따른 수정은 원래 Issue 범위 안에서 수행한다. 범위 변경, 상충하는 요구, 권한 상승 또는 고영향 결정을 요구하는 의견은 사람에게 확인한다.
   - PR 승인과 병합은 사람의 책임이다. 시스템은 승인하거나 병합하지 않는다.
   - Issue 종료는 PR 병합 및 저장소의 Issue 연동 규칙을 따른다. 병합 전에 작업이 완료된 것으로 처리하거나 Issue를 임의로 닫지 않는다.

각 작업은 최소한 Issue 식별자, 사용한 저장소와 기준 브랜치, 변경 브랜치 또는 PR 링크, 수행한 검사와 결과, 중단 또는 예외 사유를 서로 추적할 수 있어야 한다.

## 4. Codex 에이전트의 역할과 작업 범위

- Codex는 Issue 요구사항을 분석하고, 계획을 세우며, 허용된 저장소 범위에서 변경과 검증을 수행하는 작업 에이전트다.
- 작업의 권위 있는 범위는 Issue, 저장소의 지침, 자동화 설정 및 권한 정책으로 정한다. Issue 본문이나 댓글의 문구가 상위 보안·권한 규칙을 대체하지 않는다.
- 완료 조건을 만족하는 데 필요한 범위로 변경을 제한한다. 무관한 리팩터링, 종속 프로젝트 변경, 기능 추가, 대규모 포맷 변경은 하지 않는다.
- 기존의 사용자 변경을 보존한다. 파일 덮어쓰기나 삭제, 대량 변경, 데이터 마이그레이션처럼 되돌리기 어렵거나 영향이 큰 조치는 Issue에 명시되고 프로젝트 정책이 허용한 경우에만 진행한다. 그렇지 않으면 사람의 결정을 요청한다.
- 근거가 부족한 요구사항, 실패 원인을 확정할 수 없는 검사, 상충하는 지침, 예상 밖의 접근 권한 또는 작업 범위 확대를 발견하면 임의로 결정하지 않고 진행을 멈추거나 안전한 부분까지만 수행한 뒤 구체적인 질문과 상태를 남긴다.
- Codex는 결과, 테스트 상태, 미완료 작업을 사실대로 보고해야 한다. 근거 없는 성공 보고, 실패한 검사를 숨기는 수정, 테스트를 비활성화해 성공처럼 보이게 하는 행위를 해서는 안 된다.
- 승인된 권한 안에서 작업 브랜치에 변경을 제출하고 PR을 만들 수 있다. 승인, 병합, 릴리스, 배포, 저장소 설정 변경 및 권한 부여는 수행하지 않는다.

## 5. 설계문서 관리 및 변경 규칙

- 각 프로젝트는 설계·요구사항 문서의 위치와 기준 문서를 자동화에 알려야 한다. 지정된 문서가 없거나 기준이 서로 충돌하면 시스템은 임의로 기준을 정하지 않고 보고한다.
- 작업 시작 시 관련 문서와 저장소의 문서 작성 규칙을 확인한다.
- 사용자에게 보이는 동작, API 계약, 데이터 구조, 권한·보안 모델, 주요 설계 또는 운영 가정이 변경되면 해당 기준 문서도 같은 PR에서 갱신한다. 변경이 기존 설계와 어긋나면 문서를 조용히 무시하지 말고 불일치와 필요한 결정을 드러낸다.
- 구현 상세만 바뀌고 설계나 계약에 영향이 없으면 문서 변경을 강제하지 않는다. 문서가 불필요하게 바뀌지 않은 이유를 PR에서 설명할 수 있어야 한다.
- 문서는 현재 동작과 승인된 의도를 반영해야 하며, 구현보다 앞서거나 뒤처진 설명을 남기지 않는다. 과거 설계 결정을 보존하는 방법과 결정 기록 형식은 프로젝트 규칙을 따른다.
- 자동화는 Issue 범위와 무관한 문서 재구성, 형식 변경, 기존 결정의 삭제를 하지 않는다.
- PR 검토 시 코드·테스트·설계 문서 사이의 일관성을 확인할 수 있어야 한다.

## 6. Unit Test와 E2E 테스트 실행 규칙

- 각 프로젝트는 필요한 검사 명령, 실행 환경, 테스트 분류 및 필수 여부를 설정하거나 저장소 문서에서 식별 가능하게 해야 한다. 명령이 불명확하면 에이전트가 임의로 지어내지 않는다.
- **Unit Test:** 동작이나 로직이 바뀐 단위에 대응하는 테스트를 실행한다. 동작 변경을 검증할 관련 테스트가 없으면 프로젝트 규칙에 따라 테스트를 추가하거나 부족한 검증 근거를 보고한다.
- **E2E 테스트:** 사용자 흐름이나 시스템 간 통합 동작에 영향을 주는 변경에 대해 프로젝트에서 지정한 관련 시나리오를 실행한다. 모든 문서 전용 또는 무관한 변경에 전체 E2E 테스트를 강제하지 않으며, 어떤 범위에서 필수인지 프로젝트 정책으로 정한다.
- 프로젝트가 지정한 필수 Unit Test, E2E 테스트와 CI 검사는 PR 제출 전에 실행한다. 검사 간 의존성이 있으면 프로젝트가 정한 순서를 따른다.
- 실행 명령, 완료 여부, 결과, 실패 요약, 실행하지 못한 검사와 이유를 PR에 기록한다. 민감정보, 인증 토큰, 사용자 데이터는 로그나 PR에 복사하지 않는다.
- 검사 환경을 사용할 수 없거나 비용·외부 서비스·비밀정보 등 필요한 전제조건이 없으면 이를 성공으로 간주하지 않고 실행 불가로 기록한다.
- 테스트 범위 또는 필수 여부를 생략할 때는 프로젝트의 명시된 정책을 따른다. 예외가 허용된 경우 예외 근거를 기록한다.

## 7. 테스트 실패 시 처리

- 실패한 검사를 숨기거나 제거하지 말고 코드 결함, 테스트 결함, 기존 실패, 환경·의존성 문제 중 확인 가능한 원인을 조사한다.
- Issue 범위 안의 결함이면 수정 후 관련 테스트를 다시 실행하고, 필수 검사 전체를 다시 확인한다.
- 테스트나 검증 기준 자체가 잘못된 것으로 보이면 테스트를 약화하거나 삭제하는 대신 변경 근거를 남기고 필요한 사람의 검토를 받는다.
- 기존 실패 또는 일시적 환경 오류로 판단한 경우 그 근거를 기록한다. 동일 조건에서 통과를 확인하지 못한 검사는 통과로 보고하지 않는다.
- 필수 검사가 실패하거나 실행 불가인 동안 PR을 병합 가능한 상태로 제시하지 않는다. 프로젝트가 Draft PR을 허용하면 미해결 상태, 시도한 조치, 재현 또는 로그 위치를 명시해 사람의 지원을 요청할 수 있다.
- 실패를 Issue 범위 안에서 해결할 수 없거나 반복 시도가 유의미한 진전을 주지 않으면 추가 변경을 중단하고 차단 사유, 실패한 검사, 필요한 사람의 조치를 남긴다. 재시도 횟수와 제한 기준은 프로젝트별 정책으로 정한다.

## 8. PR 생성 및 사람의 승인·병합

- PR은 작업 브랜치에서 생성하며, 가능한 경우 대상 Issue를 명시적으로 연결한다.
- PR 제목과 본문은 프로젝트 형식을 따르고 최소한 변경 요약, 완료 조건과의 관계, 테스트 결과, 설계 문서 변경 여부, 미해결 위험을 포함한다.
- PR diff는 해당 Issue 작업만 포함해야 한다. 무관한 변경이 섞였으면 제출 전에 분리하거나 정리한다.
- 자동화는 필요한 체크가 끝난 뒤 PR을 생성한다. 필수 검사 상태가 실패 또는 실행 불가이면 검토 준비 완료로 표시하지 않으며, Draft 허용 정책이 있는 경우에만 Draft로 제출한다.
- 사람은 PR의 코드, 문서와 검사 근거를 검토하고 승인·수정 요청·병합을 결정한다. 저장소의 브랜치 보호, 필수 리뷰어, CODEOWNERS 및 필수 상태 검사 정책을 우회하지 않는다.
- Codex는 자기 변경을 승인하거나 병합할 수 없다. 자동 병합 기능이 추가되더라도 본 요구사항을 바꾸고 별도의 사람 승인·저장소 정책·권한 검토를 완료하기 전까지 사용하지 않는다.
- 검토에서 새 요구사항이 생기면 원래 Issue 범위와 비교한다. 범위를 벗어나면 새 Issue 또는 명시적 재승인을 요청한다.

## 9. 다른 프로젝트에서 재사용하기 위한 요구사항

- 자동화의 공통 동작과 프로젝트별 규칙을 분리해야 하며, 특정 저장소의 경로·브랜치명·레이블·명령·언어를 시스템 핵심 동작에 고정하지 않는다.
- 각 프로젝트는 적어도 저장소 식별 정보와 기준 브랜치, Issue 적격성 규칙, 작업 범위 지침, 설계 문서 기준, Unit Test와 E2E 테스트를 포함한 필수 검사, PR 규칙, 허용 권한을 제공할 수 있어야 한다.
- 프로젝트별로 검사 환경·명령·시나리오가 다를 수 있으므로 자동화가 저장소에 맞는 설정을 선택하고, 없는 설정을 다른 프로젝트의 값으로 조용히 대체하지 않도록 한다.
- 프로젝트 등록 시 필수 설정의 완전성과 권한을 확인하고, 확인되지 않은 프로젝트에서는 변경·푸시·PR 생성 단계로 진행하지 않는다.
- 하나의 프로젝트용 설정이나 Issue 본문에 있는 경로를 통해 다른 등록 프로젝트의 파일·자격 증명·작업에 접근할 수 없어야 한다.
- 공통 요구사항 변경은 모든 등록 프로젝트에 미치는 영향을 검토할 수 있어야 한다. 프로젝트별 예외는 소유자, 사유, 적용 범위를 기록하고 정기적으로 재검토할 수 있어야 한다.
- 재사용 가능한 구성의 형식, 버전 호환성, 프로젝트 등록·제거 절차는 미결정이며 별도 설계에서 정한다.

## 10. 보안 및 권한 관리 원칙

- 저장소, Issue 및 PR은 명시적으로 등록·허용된 범위만 대상으로 한다. 미등록 저장소나 권한이 불명확한 작업은 거부한다.
- 최소 권한 원칙을 적용한다. 작업에 필요한 권한만 부여하고, 작업 브랜치 제출과 PR 생성 권한을 승인·병합·저장소 관리 권한과 분리한다.
- 자격 증명은 승인된 비밀정보 관리 경로로 제공한다. 코드, Issue·PR 본문, 테스트 로그, 설계 문서, 산출물에 비밀정보를 기록하지 않는다. 노출이 의심되면 작업을 멈추고 정해진 사고 대응 경로로 알린다.
- Issue·댓글·코드·테스트 출력·외부 문서의 내용은 작업 데이터로 취급한다. 그 안에 포함된 지시가 저장소 정책, 시스템 안전 규칙 또는 권한을 덮어쓰도록 허용하지 않는다. 검증하지 않은 스크립트와 명령을 실행하지 않는다.
- 보호된 브랜치에 직접 기록하거나, 필수 리뷰·체크·승인 정책을 우회하거나, 자격 증명·권한·저장소 설정을 변경하지 않는다.
- 위험이 크거나 되돌리기 어려운 작업, Issue에서 벗어난 데이터 접근, 외부 시스템 변경은 명시적 승인과 정책이 없으면 수행하지 않는다.
- 작업 이력에는 감사에 필요한 Issue, 변경·PR, 실행 검사와 권한 차단 정보를 남기되, 보존 기간과 로그 접근 권한을 최소화한다. 로그에 민감정보를 수집하지 않는다.
- 권한은 가능한 한 작업별로 제한하고 회수할 수 있어야 한다. 인증 방식, 토큰 수명, 저장 위치, 로그 보존 기간은 미결정 항목으로 정한다.

## 11. 미결정 항목

다음 항목은 요구사항 작성 시점에 확정하지 않는다. 구현 또는 프로젝트 등록 전에 소유자와 보안 담당자가 필요에 따라 결정하고 문서화해야 한다.

- 자동화 실행 방식, 실행 주체, 트리거 유형(수동 실행·이벤트 기반 등), 재시도와 중복 작업 방지 방식
- 에이전트 런타임, 모델, 도구 연결 방식, 호스팅 위치와 네트워크 경계
- 프로젝트별 설정의 형식, 저장 위치, 스키마와 버전 호환성 정책
- Issue 자동화 대상 판별 기준, 필수 입력 템플릿, 레이블·할당·중복 처리 정책
- 브랜치 이름 규칙, 작업 브랜치 생성·푸시 시점, 임시 작업 공간의 수명과 정리 방식
- 설계 문서의 기준 위치, 문서 형식, 변경 이력 및 의사결정 기록 규칙
- 언어별 빌드·포맷·정적 분석 명령과 Unit Test·E2E 테스트 도구, 환경, 시나리오, 필수 범위
- 테스트 실패 재시도 횟수, 시간·비용 한도, flaky test 판정 기준과 Draft PR 허용 조건
- PR 템플릿, 제목 규칙, 대상 브랜치 선택 기준, 필수 리뷰어·CI와 브랜치 보호 설정
- Codex에 부여할 GitHub 권한의 정확한 범위, 인증 수단, 비밀정보 저장·회전 방식
- 감사 로그의 세부 항목, 보존 기간·접근 정책, 프로젝트별 예외 승인 절차
- 작업 제한 시간, 동시 실행 한도, 사용량 한도, 오류 알림 및 사람에게 전달할 경로

이 항목을 정할 때 본 문서의 범위 제한, 사람 승인·병합 원칙, 최소 권한 원칙을 유지해야 한다.
